Pamoja

A web platform where donors, beneficiaries and humanitarian agencies coordinate assistance, from the first request to confirmed delivery and reported impact.

How assistance moves through Pamoja

Select a stage to see who acts and which resource states apply.

    Pamoja keeps four things separate: unverified requests, pledged resources, confirmed donations and assistance actually delivered.

    At a glance

    The project in eight facts.

    Problem
    Needs, resources and progress are scattered across separate channels, so help is hard to find, track and measure.
    Solution
    One platform for requesting, assessing, pledging, allocating, delivering and reporting assistance.
    Users
    Donors, beneficiaries and humanitarian agencies (NGOs, charities, community organizations).
    Category
    Humanitarian technology, web-based.
    Stack
    React.js, Python Flask, PostgreSQL, SQLAlchemy.
    External data
    ReliefWeb for humanitarian updates, with a public dataset as fallback.
    Delivery
    Three phases aligned to Moringa School Projects 1 to 3, run with Agile and Scrum practices.
    Team
    Group 8: Julius Irungu, Eugene Okoth, Harmon Moindi, Ralph Njuguna.

    Quality attributes

    • Usability: intuitive navigation, understandable workflows.
    • Responsiveness: desktop, tablet and mobile.
    • Performance: efficient page loads under normal use.
    • Accessibility: readable type, accessible controls, good contrast.
    • Security: secure authentication, authorization, validation.
    • Maintainability: modular code, consistent practices.
    • Reliability: graceful handling of bad input and failed API calls.
    • Privacy: sensitive records visible only to authorized users.

    Safeguards and risks

    Pamoja may handle information about vulnerable people, so privacy comes first.

    Safeguards

    • Data minimization: collect only what coordination needs.
    • Consent: tell beneficiaries how data is used and shared.
    • Access control: sensitive data for authorized roles only.
    • Agency verification: review organizations before verified status.
    • Fraud prevention: separate unverified claims from assessed needs.
    • Financial safeguards: no collecting or holding of funds in early phases.

    Main risks

    • API restrictions: verify access early, keep an alternative.
    • Limited time: build the minimum viable features first.
    • Sensitive data: use fictional test data until safeguards exist.
    • Fraudulent requests: require agency assessment.
    • Scope growth: keep future enhancements separate.
